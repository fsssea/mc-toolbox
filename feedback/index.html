BOARD / 漏洞看板

每条漏洞一个固定编号，修到哪一步都看得见。

提交后登记成 BUG-N，固定链接是 feedback/bug-N/，编号一旦分配就不再变。这里按「重要待修 → 病又复发了 → 正在修复 → 已修复 → 设计的特性 → 不存在的漏洞」排，并标出它出现在哪些版本。

还没有登记的漏洞。

待定 · 等待定级

刚提交时的状态，由管理员定级为下面六种之一。

重要 · 待修

已确认，影响面大，排在修复队列最前。

病又复发了

之前修好过，但新版本里又出现了，按新漏洞重新登记。

正在修复

已经动手改，验证用例补完就合入。

已修复

修复已随公开发布版本上线，页面会写明修复版本。

设计的特性

看起来像 bug，但这是刻意设计的行为，页面会写清原因。

不存在的漏洞

无法复现、用法问题或环境问题，不构成漏洞。

状态和修复版本由维护者更新；一条漏洞从「重要 · 待修」走到「已修复」，过程都会留在它自己的页面上。

REPORT / 提交反馈

填好这五项，基本就不会来回问了。

生成的内容会先填进 GitHub 的 Issue 表单，你确认后再点提交；不想用 GitHub，也可以复制全文发到 B 站私信或视频评论区置顶留言。

BUG-?
编号按提交顺序分配，第一个反馈的漏洞为 BUG-1；提交后页面地址固定为 feedback/bug-N/。

提交前先搜一下已有 Issue，避免重复；不要把个人存档、账号、聊天记录贴上去，需要样本时请脱敏或只描述结构。

db 是存档最重要的数据文件夹。为了排查问题需要你提供样本时，请先「导出存档」备份，再在副本上操作。
HOW TO / 怎么写才有用

三条就够，别写小作文。

能复现的步骤 + 报错原文 + 版本平台，基本一次就能定位；只写「打不开」「坏了」通常要多来回三轮。

01

能复现

从打开软件到出问题的每一步，按顺序写；能附截图就附，报错弹窗整段复制。

02

说清楚环境

哪个端、什么系统版本、存档多大、是不是从别的版本转过来的包。

03

给样本

能提供最小复现包最好；给不了就描述文件结构，别直接传整份存档。

FAQ / 常见问题

关于反馈这件事。

一定要 GitHub 账号吗？

提交 Issue 需要；只看不用。没有账号就把表单内容复制下来，发到 B 站私信或视频评论区，我一样会看。

多久会修？

崩溃、存档写坏这类先修；界面与体验类按批次排。修好后会在对应 Issue 里回一句「已在 1.0.x 修复」，你可以回来查。

能提功能建议和汉化问题吗？

可以，类型选「功能建议」。汉化缺词、错译请附上原文与截图，方便直接改。

会不会把我存档传上去？

不会自动上传。软件全离线运行；只有你自己在 Issue 里主动附加的文件才会公开，贴之前请先脱敏。
